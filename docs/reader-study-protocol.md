# Formative reader qualification protocol

Status: prepared, not executed. This is the five-person formative assessment required by WS6. Headless browser assertions establish interaction mechanics; they do not supply human observations or utility evidence.

Freeze one tested runtime/skill/tarball, the selected project snapshot, exported reader revision and browser version before recruiting readers. Use a representative project with an independently checked canonical concept, a source binding, an inferred relationship, an incoming consumer and an explicit historical comparison. The small installed two-root fixture can verify the protocol mechanics but cannot stand in for representative project utility. Keep a direct-source baseline available. An independent reviewer must establish the answers and relevant uncertainty from source before observing participants.

| Task | Prompt given to the reader | Independent success criterion |
| --- | --- | --- |
| Find the responsible concept | Locate the accepted explanation for the selected behaviour and show the implementation evidence behind it. | Correct concept and source; reader identifies freshness/trust limits rather than equating a generated index with review. |
| Check an inferred relationship | Explain the displayed relationship and say what has and has not been established. | Reader distinguishes inferred prose and candidates from source-qualified navigation and canonical knowledge; inspects supporting evidence and abstains where it is insufficient. |
| Inspect incoming impact | Find the evidenced incoming consumer of the selected implementation. | Correct source-qualified consumer; unresolved/dynamic candidates and omitted coverage remain visible in the answer. |
| Compare the change | Compare the selected historical source with the current version, then return using a saved location. | Correct before/after identity and location; reader does not infer historical canonical freshness or test execution from byte comparison. |
| Handle incomplete evidence | Determine what can be concluded when the comparison root or requested record is unavailable. | Reader recognizes the partial/denied boundary and does not treat missing evidence as a clean empty result or authorize wider access. |

Use five participants who have not authored the feature. Give each the same source task, counterbalance reader-first versus direct-source-first ordering, and reset navigation between tasks. Do not coach toward a specific confidence label. Where a task requires reading a graph, allow the documented bounded neighbourhood rather than adding an unrestricted whole-repository graph for the study.

Record only anonymous trial IDs in local study results: task ID; artifact/project/revision identities; baseline or reader condition; completion outcome; correctness and evidence rubric; unearned-confidence incident; elapsed task time; attempts/backtracks; keyboard/mobile issue; and a short observation grounded in the action. Keep participant identity and contact details outside the project artefacts. Preserve abandoned and unsuccessful tasks. Unknown timing stays unknown, not zero.

After all five sessions, review each failed reader task and uncertainty mistake. Fix observed failures at their owning layer, add a nearby regression, and repeat affected tasks on a fresh artifact. Do not declare utility from attractive screenshots, task completion alone, or a synthetic client fixture. Report browser/accessibility mechanics, observed human outcomes and broader limitations separately. Any participant briefing or external scheduling remains a separate explicitly authorized action.
