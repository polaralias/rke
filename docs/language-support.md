# Structural support and qualification

Support is evidence specific. No grammar is labelled compiler grade solely because it loads. File API reports static fixture qualification separately from broad extraction.

| Profile | Maintained evidence | Boundary |
| --- | --- | --- |
| TS/JS, including JSX/TSX, MJS/CJS | relative/default value imports, local export aliases and imported reexports, explicit-over-star precedence, qualified seeds, explicit receiver construction/types, duplicate-name isolation; maintained parameter/ancestor/local shadow and class namespace cases | type-only and hidden exports cannot certify calls; block bindings conservatively apply to their containing function; ambiguous stars, runtime injection and overload semantics require source review |
| Python | scoped imports, aliases, class receivers and separate bare lexical lookup, parameter/ancestor/local/module rebinding and comprehension uncertainty; [Pyright 1.1.414 minimal project qualification](release-completion-report.md) | runtime-selected handlers, control-flow-sensitive scope and indirect type inference are not statically certified |
| Java | class imports, enclosing-class bare calls, unrelated-class exclusion and overload ambiguity | broader scope, instance/inheritance/build semantics require explicit server or source review |
| Kotlin and C# | enclosing-class bare calls, unrelated-class exclusion, delegate parameter/local binding shadows | broader imports, inheritance/interface/build semantics and project/server qualification remain open |
| Go | local module imports and package isolation; default imports use unique declared package names, aliases remain explicit; exported top-level package functions and private same-package calls; receiver-qualified method identities; explicit local concrete-struct receivers, typed parameters/variables and single composite-literal bindings resolve unique direct methods across regular same-package files; literal directory boundaries and lexical shadows | interfaces, aliases, generic types, imported receiver types, promoted methods, reassignment and local type shadows remain unresolved; default-import lookup is capped at 500 declarations; block/closure shadows conservatively cover the containing function; escaped strings, external modules and build semantics require explicit server or source review |
| Swift | same-file concrete nominal types and unconditional extensions retain qualified methods; own bare calls and explicit `self` resolve unique direct methods; protocol requirements remain distinct declarations; maintained parameter/local/overload/dynamic-selector exclusions | protocol requirements/extensions do not establish concrete dispatch; unrelated methods cannot qualify bare calls; arbitrary receiver types, cross-file module/extension ownership, conditional extensions, generic constraints, inheritance and builds require explicit server or source review |
| PHP | semicolon/braced namespace-qualified function/class/trait identities; same-file namespace-relative and absolute functions, explicit instance and public static methods; flat explicit trait use retains its defining method and class overrides take precedence; visibility and incoming identity checks | namespace imports, missing namespaced functions/global runtime fallback, arbitrary receivers, late binding, abstract methods, conflicting/adapted/nested/missing traits and cross-file include/autoload semantics remain unresolved |
| Other loaded grammars | definitions/text extraction and maintained corpus examples | no broad cross-file semantic guarantee; digest-bound agent review can supplement extraction |

| Real Java LSP | [Eclipse JDT LS 1.61.0 with JDK 23.0.2 initialized two-file project qualification](release-completion-report.md): cross-file call and configuration expiry | cold startup changed project metadata and was refused; subsequent stable project qualified; no Android/Kotlin/Maven/Gradle or full plugin/JDK attestation |
| Real C++ LSP | [clangd 22.1.6 C++17 header/caller project qualification](release-completion-report.md): cross-file call and compilation-database expiry | no actual compiler, platform SDK, standard library, template/macro or full extracted-resource attestation |
| Other LSP servers | bounded generic stdio adapter and containment tests | independently qualify each installed server/project pairing before advertising semantic coverage |

Use `node dist/scripts/qualify-language-server.js <python|typescript|go|rust|cpp|java> <host-configured-profile>`. Each fixture creates and removes its own disposable Git project, invokes the shared public operations and requires a cross-file server-reported call before checking configuration invalidation. The Java fixture permits one independently checked cold `.project` initialization followed by a fresh resolution; the initial changed-input attempt remains refused. Source/classpath changes or new nonignored files cannot pass this preparation boundary. The selected profile's language must match the fixture. The report binds the server implementation digest; record the installed version alongside that digest independently. An unsupported call hierarchy/position capability exits 3 and remains unqualified. Adding a fixture is not executed real-server evidence. This runner does not install or select an executable from repository content. Re-run semantic resolution after changing ignored dependencies, undeclared server dependency or environment inputs. See [cross-language evidence](cross-language-evidence.md) for dated results and agent costs.

Server profiles must declare implementation identity inputs; see the [profile setup contract](../.agents/skills/rke/references/language-server-profiles.md). Repository-owned profile files and executable inputs are rejected.

The maintained [public lexical-scope cases](../tests/language-fidelity.test.ts) distinguish shadowed imported calls from an unaffected caller and preserve local callable/receiver evidence. Their presence alone does not qualify a language; executed build-specific results are recorded in the [progress ledger](repository-intelligence-progress.md). Broader Java/Kotlin/C#, Go/PHP/Swift and real-server work remains open.

Go call extraction preserves Unicode identifiers, parenthesized function targets and qualified package names through syntax-tree fields. Indexed receivers and factory-returned receivers retain explicit dynamic target markers instead of being truncated into bare same-name functions. Direct methods have base-type-qualified identities, so `Service.Save` and `Other.Save` remain separate incoming targets. Simple value/pointer receivers resolve only when a unique non-generic concrete struct and direct method exist in the same regular package directory. Typed parameters, named results, explicit variable types and single `T{}`/`&T{}` bindings supply bounded type evidence. Bare calls cannot select instance methods. Interfaces, aliases, generic/local types, duplicate declarations, inconsistent packages, reassignment and anonymous-function shadows withhold confirmation; no compiler or precise control-flow qualification follows. Method expressions, promoted methods, imported receiver types and factory/new inference remain outside this slice. The [Go specification](https://go.dev/ref/spec#Method_declarations) defines the receiver base-type and selector rules informing this boundary.

Swift's grammar represents nominal types and extensions with the same declaration node; indexed declaration evidence distinguishes them before confirming an own-type method. Protocol requirements are exposed as interface/method declarations, while protocol extension calls remain unresolved as concrete targets. Simple syntax-derived selectors preserve their operand; indexed and factory operands retain dynamic markers. Parameter, property and assignment bindings conservatively withhold shadowed bare calls. This is maintained same-file navigation, not module/compiler qualification or general type inference. The [official extension rules](https://docs.swift.org/latest/documentation/the-swift-programming-language/extensions/) permit extending both nominal and protocol types, which is why declaration kind alone cannot confirm dispatch.

PHP extraction records namespace context independently of class/function nesting, including global blocks and named functions declared inside other functions. Call markers distinguish absolute, namespace-relative, relative, static and receiver syntax; dynamic targets retain uncertainty rather than a bare method suffix. Resolution uses unique same-file declarations and respects instance/static and public/private boundaries. Plain flat trait use may select one defining method across at most 32 explicitly declared local traits; a class's own method takes precedence. Conflicts, aliases/adaptations, nested or unknown traits and abstract requirements withhold certainty. Namespace import tables currently cause nonabsolute calls to abstain rather than guessing an alias, and missing namespaced functions do not certify runtime global fallback. Cross-file include/autoload, inherited implementations and arbitrary receiver typing need separate source or server evidence. These boundaries follow the [PHP name rules](https://www.php.net/manual/en/language.namespaces.rules.php) and [trait precedence rules](https://www.php.net/manual/en/language.oop5.traits.php), without claiming interpreter qualification.

Semantic preparation uses the UTF-16 columns returned by this JavaScript Tree-sitter runtime. Receipt schema 4 records that position contract and excludes older receipts. The Unicode regression includes astral text and repeated function-name text before the definition; a mock transport validates the actual requested position. It establishes adapter behavior rather than a real-server project pairing.
