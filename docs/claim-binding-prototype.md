# Selected claim binding prototype

Status: Stage 3 prototype, 2026-09-27. The optional tracked format is `.rke/claim-bindings.json` (schema version 1). It selects a small number of consequential document sections; the existing `.rke/repo-context.json` continues to cover whole-document knowledge freshness. No SQLite table or new CLI/MCP operation is needed. `rke documentation assess --base <ref>` returns claim assessments alongside the existing knowledge impact.

## Acceptance cases and format decision

The seven executable cases in `tests/claim-bindings.test.ts` cover an unchanged source move, a same-path behavior change, two equal move candidates, unsupported source with and without a digest-bound review, an explicitly requested review that cannot fall back to grammar availability, a changed document section, and integration with exact-delta no-update refusal. A move gives `review-needed` with a candidate path and does not rewrite the selector. A changed source or section gives `review-needed`. Duplicate candidates and unsupported source without a current agent review give `unresolved`. The prototype has one tracked binding for the architecture section on CLI/MCP parity. Its three exact source selectors remain `current` in the working tree after the local test suite passed. This is evidence of unchanged reviewed identities, not a fresh behavioral proof.

Each claim records a stable ID, a document path and unique Markdown heading, the exact section digest, a human review decision, and one to eight source selectors with roles (`interface`, `implementation`, `test`, or `runtime-probe`), paths and digests. Section text survives unrelated line shifts; duplicate headings cannot silently select the wrong section. A changed digest requires review. A moved file with identical bytes is only a candidate. The inspectable JSON is the review record. For unsupported source, an `agent-reviewed` selector also requires a current digest-bound local code review; that derived cache is not a substitute for the tracked decision.

The format costs one section digest and one file digest per selector per review. On the current RKE checkout, assessing its one claim and three selectors took 170 ms in one Windows run, without a SQLite projection. Whole-file hashes deliberately request review even after a comment-only edit; this is a conservative false positive, and maintaining hundreds of bindings would be burdensome. The 25-claim and eight-selector limits keep it opt-in for important behavior. Hashing move candidates uses the existing bounded, secret-aware source evidence reader. The current resolution is file-level; grammar availability is reported separately and does not claim a resolved symbol edge.

An assessment keeps four propositions apart: a selector resolves, reviewed source bytes are unchanged, a test executed, and the behavior statement is true. The last two are always `not-observed` and `not-assessed` in the claim result. EWF reads source, runs focused tests where needed, and confirms or edits the durable statement. An exact-delta no-update disposition remains possible when no canonical binding is affected and all selected claims are current; it requires every changed path and a substantive reason. A selected claim needing review blocks that disposition, including at closure receipt revalidation.

## Limits

The prototype does not infer semantic equivalence from matching bytes at a new path, detect every indirect dependency, execute tests, or automatically approve a changed statement. Existing broad knowledge impact and `repo change impact` provide additional candidates for the agent to inspect. The binding file remains optional, and a `current` binding is a freshness result only. More semantic selectors or a SQLite projection require a measured missed claim or repeated resolution cost in a real task.
