# Exact-artifact release qualification

RKE 0.1.0 is the initial development version. EWF and the runtime adapter are independently versioned packages. The [candidate declaration](release-completion-status.json) uses schema 3 and deliberately contains no prior release or hosted-pass projection. `node dist/scripts/validate-candidate.js` checks actual package/skill versions, the Tasks workflow pin and ledger agreement. It reports `initial-candidate-unqualified`; `--require-qualified-source` refuses this declaration. Optional `--tarball` captures the actual SHA-256; `--mirror` validates source provenance. None of these operations grants release approval.

`npm run validate:release` checks the inner-loop package contract. Publication separately requires Node >=24.15, clean identified source, byte-identical committed methodology/package inputs, the exact `v<version>` tag, ancestry in `origin/main`, complete runtime and both skill identities, and a reviewed exact-artifact receipt. `node dist/scripts/validate-publication.js --qualification RECEIPT.json --tarball PACKAGE.tgz` validates that receipt before publication. Do not rebuild after qualification.

Receipt schema 1 contains `scope` (`developer-preview`, `public-beta` or `complete`), `sourceCommit`, `version`, `runtimeDigest`, `skillDigest`, `adapterDigest`, `tarballIntegrity`, `reviewedAt` and exactly seven distinct `gates` (G0–G6). Each gate has a substantive `evidence` reference. Passed gates bind the current artifact digests. `complete` requires every gate to pass. `public-beta` permits only G5 to remain pending, with its study limitation explicit. Schema, hashes and green fixtures cannot judge independent engineering outcomes.

For the explicitly selected `developer-preview` scope, G0–G5 may remain pending with substantive explanations; failed gates are still rejected and G6 must pass. The receipt must state independent-qualification limitations and include exactly five passed `mechanicalChecks`: `hosted-ci`, `reproducibility`, `deterministic-tests`, `packed-install` and `publication-hygiene`. Every check needs reviewed evidence and the exact source commit, version, runtime/skill/adapter digests and tarball integrity from the receipt. Missing, duplicate, failed, skipped, pending or stale mechanical checks block publication. Full CI includes the existing typecheck, lint, complete deterministic and independent contract suites, release contract, no-Python check, supported-platform matrix and package smoke. Hygiene includes reviewed source/history and packaged-file checks. Preview approval does not mark independent agent, host, reader or effectiveness qualification as passed. The README and release notes identify v0.1.0 as a developer preview.

The protected npm environment supplies reviewed JSON via `vars.RKE_RELEASE_QUALIFICATION`. Missing, stale or incomplete evidence blocks publication. The publisher refuses conflicting registry integrity. Versioning, tagging, history cleanup and local tests never authorize publication.

The [repository intelligence acceptance contract](repository-intelligence-acceptance.md) and [original-skill matrix](legacy-skill-parity-matrix.md) are independent obligations. [Study preregistration](agent-study-contract.md) retains its protected cohort and thresholds. Lack of approved trials or human participants leaves qualification open.

CI targets Node 24.15 and maintained Node 24 on Linux, Windows and macOS. The independent OKF Tasks workflow pins `99a2907181c029446ffaf9c6bff664a7b0ff487c`, with strict contracts and no skips. Its Python environment belongs to the external producer; RKE runtime and distribution remain TypeScript. No hosted result is claimed before this exact committed artifact executes there.

## Verification and publishing authority

The tag workflow follows the same verify-then-publish split as OKF Tasks. Its source checkout, complete deterministic verification, installed-package smoke and exact-artifact qualification run with a read-only GitHub token. Only after qualification does it upload the tested tarball and expose its version/integrity as job outputs.

The npm publisher has no source checkout and runs no repository code. It downloads the verified artifact, checks its SHA-512 against verification output, refuses registry conflicts, and invokes trusted npm with lifecycle scripts disabled. OIDC and attestation permissions exist only in that publishing job. Configure npm trusted publishing for `polaralias/rke`, workflow `publish-release.yml`, environment `npm` after the bootstrap publication described below; this setup does not itself publish a version or create a tag.

The GitHub-release job runs only after successful npm publication or exact-integrity readback. It consumes the same artifact without source checkout, and promotes the existing draft or creates one release for the tag. Release Drafter is restricted to trusted `main` and derives its draft version from `package.json`.

## First npm publication

The npm organization and GitHub owner are both `polaralias`; the public package is `@polaralias/rke`. Verify the authenticated npm account and organization access separately. `package.json` declares the public Git repository for provenance and fixes the publishing registry and public access. The first release uses the same reviewed tarball, source/tag checks and qualification policy as subsequent releases.

An npm package must exist before its trusted publisher can be configured. To bootstrap with CI provenance, a maintainer supplies a temporary, narrowly scoped `NPM_BOOTSTRAP_TOKEN` as a secret in the GitHub `npm` environment. The workflow exposes it only to the npm publish step, after verification has uploaded the tested tarball. It is not available to the source checkout, dependency installation or repository scripts. Never put this credential in source, documentation, receipts or chat. A local npm login does not authenticate a GitHub runner.

After the first successful publication, configure npm trust for GitHub owner/repository `polaralias/rke`, workflow filename `publish-release.yml`, environment `npm`, with direct publishing allowed. Keep those identifiers exact. Remove the temporary GitHub environment secret and revoke its npm token after verifying the trust configuration. Subsequent releases authenticate with OIDC. npm documents [trusted publishing](https://docs.npmjs.com/trusted-publishers/) and the [trust CLI prerequisites and flags](https://docs.npmjs.com/cli/v11/commands/npm-trust/).

The first-publish credential is only an authentication mechanism. It does not satisfy the independent qualification gates, authorize an unreviewed source/tag or bypass the artifact integrity checks. Missing qualification still blocks publication.

The default-branch ruleset requires one approval, code-owner review, resolved conversations and successful `release-gate` plus both supported real-Tasks integration checks. Force pushes and branch deletion are blocked for ordinary updates. Repository administrators may bypass the rules, matching the explicitly selected OKF Tasks policy. `repo-admin.json` records the maintained policy; GitHub readback establishes the actual installed rule.
